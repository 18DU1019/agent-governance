# 跨端 Skill 正本治理纪律（Junction Discipline）

适用场景：同一套 skill 目录被多个 AI Agent 端（如 TRAE / WorkBuddy / Claude Code 等）共同加载时，如何保证"一份正本、多端挂载、可校验、不产生分叉"。

## 一、挂载模型

- 正本目录（source of truth）存放实体文件；各 Agent 端的 skills 目录内对应项为**链接**（Windows NTFS junction / Unix symlink），指向正本同名子目录。
- 禁止"每端各存一份副本"——副本必然漂移，且漂移以"内容看似相同、字节不同"的隐性形态积累。

## 二、四条纪律（违反即事故）

1. **正本目录内禁止再建任何链接**——防止链接环与递归扫描事故。
2. **卸载链接只用 `rmdir <链接名>`（不带 `/S`）**——对链接路径使用递归删除会穿透删掉正本。全程禁用 `rd /S` 作用于链接。
3. **链接所在的各端目录永不入 git**——git 不理解链接语义，会把指向内容当实体重复跟踪；版本仓库只建在正本目录。
4. **备份命令必须排除再解析点**——Windows `robocopy` 需加 `/XJ`，防止跟随链接造成数据重复或放大。

## 三、一致性校验器设计要点（sync_check.py 的设计依据）

- **自动发现挂载，不维护硬编码名单**——名单制无法发现"漏挂/多挂"，且每次挂载变动都要改脚本。
- **遮蔽检测**：某端出现与正本同名的**实体**目录即为事故形态（说明该端实际加载的是副本而非正本），必须报错并判定"内容相同"还是"已分叉"。
- **身份配对按 SKILL.md 内部 `name` 字段，不按目录名**——目录名与内部名不一致会造成系统性伪分叉/伪一致。
- **跨端比对先归一化行尾再哈希**——不同工具链产出的 CRLF/LF 差异会制造大量"字节不同、内容相同"的伪分叉；凡跨端比对，先 norm() 后 hash，并区分报告"字节一致"与"内容一致"两档。
- **对链接做可达性判定要用心**：Windows 目录联接在部分 API（如 `os.path.islink`）下返回 False，须用 reparse point 属性判定。

## 四、变更门禁

- 改动正本的 **skill 内容** 后，各端需重开会话做**双向触发测试**：正向触发命中率 >90%，负向抽检误触发 <5%。
- **维护件豁免**：校验脚本、README、裁定记录等不被加载器读取的文件，其改动不触发门禁。
- 门禁针对"被 Agent 实际加载的内容"，这是判定豁免边界的唯一标准。

## 五、台账纪律

- 挂载结构变更（建链/拆链/收编/隔离）当日登记，含回滚命令；被替换的旧副本按**零删除原则**移出原位归档，不物理删除。
- 任何"两端不一致"的结论，先排除三类伪差异：行尾异构、展示层截断、配对键选错。
