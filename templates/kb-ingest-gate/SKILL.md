# 知识库入库闸门与内容治理（kb-ingest-gate）

> 血缘（lineage）：`version` 字段沿用生产正本同号（2.1.5），仓内模板为脱敏衍生件；同步方式=生产正本修订时手动回灌模板并同步 version；supersedes: null（模板无被替代旧版）。仓内版本与生产正本的对照以本字段为准，不再依赖口头记忆。

## 一句话定位
用户有"交付文件即时入库"的好约定，但曾两次翻车：
1. 把项目目录里已有的原始缓存/脚本/CSV 又复制一份塞进 KB（一次 17MB 复制品）；
2. "一股脑全入库"后内容散乱、缺整合总结、MOC 断链；
3. **更惨的一次**：清理 KB 时，WorkBuddy 后台 git 自动同步在每个 `commit` 后把工作区大量文件物理删除，连带把 3 个从未被 git 跟踪的用户文件永久删掉且无法恢复。
本 skill 用四道闸门解决：Phase 0 防 git 破坏（头号风险）、Phase 1 入库前挡垃圾、Phase 1.5 按 AI-16 规范入库、Phase 2 入库后收拾散乱、Phase 3 用 AI-17/18/19 三把标尺复检收尾。

## 何时用（触发词）
- 入库类：用户说"入库""闭环""归档""交付文件进 KB""整理知识库"
- 治理类：用户说"梳理整合""查漏补缺""检查有没有闭环""一股脑了需要整理""总结一下"
- 复检类：用户说"用 A-17/18/19 检验""三标尺复检""闭环检验"
- 任何准备 `git add` / `git rm` / 写文件进 `<YOUR_VAULT_PATH>\` 的动作
- 边界：KB 位于知识库所在盘（可写），不受只读受限盘的写入限制；但改只读受限盘上的资料仍须先问用户

## 范围约束（默认只针对本次对话内容，硬边界）
- **默认 scope = 本次对话产生的文件与产物**。用户说"入库/闭环/整理/查漏补缺/检查闭环"时，只动本轮会话里生成或明确点名的文件，**不扫全库、不波及 KB 里其他人或其他会话的内容**。
- 为什么设这条：曾两次踩坑，根子都是"范围失控"——① 一股脑把全项目复制品塞进 KB；② 第二仗清理时，误判 + 后台同步连累了别人未提交的 MOC/README 本地改动，甚至误删合法笔记。范围失控是事故放大器。
- **不碰别人的东西**：KB 里若有人正在改的文件（`git status` 显示 `M`，且非本次对话产生），一律不动；未跟踪的 `??` 若不是本次产物，只盘点、不处理、不删（见 Phase 0.3）。
- **扩展 scope 必须显式 opt-in**：若用户想清历史遗留（如"第二仗"清理早年进 KB 的源码），需用户**明确点名范围**；此时当作独立的"一仗"，先调查（MD5/清单/链接扫描）再动手，绝不与本次对话产物混着清。
- **查漏补缺与三标尺复检也只验本次**：断链检测、孤儿笔记检查、产物对账，只针对本轮新增/修改的链接与文件，不做全库地毯式扫描（除非用户明确要求"全库体检"）。

## ⚠️ Phase 0：动手前的 git 安全门（最重要，必须最先做）

知识库是 git 仓库，且 WorkBuddy **可能开着后台 git 自动同步/自动提交**。实测曾发生：每次 `git commit` 后，后台同步把工作区大量文件当"多余"物理删除（`git status` 突然冒出几百个 `D` 标记），并连带删除未跟踪的用户文件。
**Phase 0 的目的就是把这种毁灭性风险挡在动手之前。任何 git 写操作前，先跑下面的"前检命令块"。**

### 0.1 前检命令块（每次 git 操作前必跑）
Git Bash（须 `dangerouslyDisableSandbox:true`）：
```bash
cd "<YOUR_VAULT_PATH>"
# 1) 清掉残留死锁（不清理会让后续 git rm 循环错乱、误删计划外文件）
rm -f .git/index.lock
echo "--- 未跟踪文件(状态 ??)：最危险的一类，有价值先备份 ---"
git -c core.quotepath=false status -s | grep '^??' || echo "(无未跟踪文件)"
echo "--- 当前 HEAD(记住它，破坏后可整体恢复) ---"
git -c core.quotepath=false rev-parse HEAD
echo "--- 工作区是否干净 ---"
git -c core.quotepath=false status -s
```

### 0.2 自动同步的处置：能关则关，**不能关就走 0.6 安全协议**
- **先问用户**：WorkBuddy 设置里的"知识库 git 自动同步/自动提交"能不能关？
- 用户说**不能关**（2026-08-15 明确：自动同步不能关）→ 所有 git 写操作默认按"自动同步开着"设计，照 0.6 协议执行，**绝不在未防护下直接 commit**。
- 用户说已关但仍反复被破坏 → 用 `automation_update`(mode=list) 排查**可能执行 git 的自动化任务**（如"月度知识库迭代""周末知识库整理""知识库迭代反馈每周汇总"一类），用 `automation_update`(mode=update,status=PAUSED) 暂停之。

### 0.3 未跟踪文件（??）是头号雷区 —— 必须盘点 + 备份
- 未跟踪文件**不受 git 保护**：一旦后台同步破坏工作区，它们会被一并删掉，且 git 历史里没有、**回收站也大概率搜不到，无法恢复**（已发生过 3 个文件永久丢失的事故）。
- **规则**：前检发现 `??` 文件时，先判断是否有价值；有价值的（如用户手写笔记、未提交的报告），先复制到安全位置（如 `<WB_HOME>\backup\` 或项目目录），再继续 git 操作。
- 绝对禁止"先 commit 清理，再回头想未跟踪文件"——等你回头，它们可能已经没了。
- **高危命令红线 `git clean -f*`**：`git clean -fd`（`-f` 强制、`-d` 清目录）会**物理删除所有未跟踪文件**，正是本条 0.3 的头号雷区命令——不受 git 保护、无法恢复、回收站搜不到。**任何时刻禁止在备份前对含未跟踪文件的目录执行 `git clean -f*`**；确需清理，先按 0.4「稳三招」归档未跟踪文件后再逐个处理。（2026-09-27 自 AI-66 P3 外部文对照补入）

### 0.4 大批量删除的"稳三招"
1. **先归档、后删除（零丢失底线）**：要删的 KB 文件，先 `cp` 到项目目录的 `<PRIVATE_SYSTEM>\.kb_archive\YYYY-MM-DD\`（保留相对结构），再删 KB 里的。这样即使误删也能找回。
2. **小批、单步、即时核对**：不要一个循环里连删几十个。每删 1~3 个就 `git status` 看一眼；发现意外 `D` 立刻停手。
3. **删前再清一次 index.lock**：每次 `git rm` / `git commit` 前都 `rm -f .git/index.lock`，防后台竞态。

### 0.5 已被自动同步破坏工作区 → 急救（别再用 commit 补救！）
症状：`git commit` 后 `git status` 突然冒出几百个 `D`（整个目录被标记删除），但 `.git` 历史完好。
正确做法（**千万不要为了"修好"再 commit，那会再次诱发破坏**）：
```bash
cd "<YOUR_VAULT_PATH>"
rm -f .git/index.lock
# 整体恢复到 HEAD（索引/历史完好 = 安全，可救回一切已提交内容）
git -c core.quotepath=false checkout HEAD -- .
# 验证：磁盘文件数应与 git tracked 数吻合，关键笔记在位、误删笔记已回
git -c core.quotepath=false status -s   # 应干净，无 D
```
恢复后：**停止新的 commit**，先让用户关掉自动同步，再评估剩余工作。

### 0.6 自动同步开启（不可关闭）下的安全操作协议 ★2026-08-15 用户明确
用户已明确"自动同步不能关"。因此 git 写操作按以下协议，**防止再次诱发工作区破坏**：
1. **首选"少 commit"**：知识库写入用文件系统直接落位（`cp` / Write 工具），Obsidian 不依赖 git 即可正常读取；git 提交攒批、低频、经用户确认后再做，避免每次 commit 触发同步竞态。
2. **必须 commit 时，先快照后提交**：commit 前对工作区做防护快照——
   ```bash
   cd "<YOUR_VAULT_PATH>"
   # 快照：记录当前全部文件的清单+哈希（轻量，不拷贝全库）
   find . -type f -not -path './.git/*' -exec md5sum {} + > "<WB_HOME>/backup/kb_snapshot_$(date +%Y%m%d_%H%M%S).txt" 2>/dev/null
   ```
   commit 后**立即** `git status` 比对；发现意外 `D` 或文件数骤减 → 立即 `git checkout HEAD -- .` 恢复（见 0.5），恢复后停止 commit。
3. **精确 add，不扩大面**：只 `git add <明确列出的文件>`，**禁用 `git add .` / `git add -A`**，减少同步感知的变更面。
4. **破坏若复现**：记录现象与时间点（每次破坏都发生在 commit 后？破坏的文件范围？），协助定位真元凶（WorkBuddy 自动同步 / Obsidian Git 插件 / 云盘同步），**不臆断根因**，把证据给用户判断。
5. **入库不 commit 也能闭环**：交付 = 文件落位 + MOC 接链 + 三标尺复检；git 留痕只是加分项，不是闭环的必要条件（自动同步开启期间尤其如此）。
6. **他人暂存区内容必须用限定路径提交避开** ★2026-09-11 实测新增：KB 里常驻有 Agent 端记忆产物目录（如 `<AGENT_HOME_TRAE>` 侧沉淀件）大量**已 staged** 的 `M` 状态文件。若直接 `git commit -m`，会把它们一并提交，违反"不动他人暂存文件"的范围约束。正确写法是**限定路径提交**，只提交本轮产物：
   ```bash
   # 0) 删锁前必须先确认没有并发 git 进程（硬规则：tasklist 连查两次均无 git.exe，且锁文件超时未更新，才可删）
   tasklist | grep -i "git.exe"        # 无输出才继续；有输出直接停下，说明有并发写者
   if [ -f .git/index.lock ]; then rm -f .git/index.lock; fi
   git add "本轮/新文件.md" "本轮/改动的MOC.md"        # 只 add 自己的（未跟踪新文件必须先 add）
   git commit -o -m "msg" -- "本轮/新文件.md" "本轮/改动的MOC.md"   # -o/--only，等价于 commit -- pathspec
   ```
   **选项顺序是硬约束 ★2026-09-16 实测踩坑**：`git commit` 的所有选项（`-o`、`-m`）**必须写在 `--` 之前**。写成 `git commit -o <paths> -m "msg"` 会报 `error: pathspec '-m' did not match any file(s) known to git`，`-m` 与消息正文被整体当成 pathspec 解析，提交根本不发生。更隐蔽的是**失败后文件仍留在暂存区**（staged 由基线 31 变成 33），若紧接着重跑脚本并仍用"提交前的 staged 数"当基线，会把基线误记为 33，于是第 103 行第 ② 项校验（"其余 staged 条目数与提交前一致"）形同虚设、什么都验不出来。正解：提交失败后先 `git status --porcelain` 确认真实暂存内容与数量，重跑时以**上一次成功提交对应的干净基线**为准（2026-09-16 本轮为 31）。
   机制说明：`git commit [-o|--only] <pathspec>` 只提交匹配路径的变更，暂存区里其他文件（含 `_agent/` 的记忆改动）保持原状态不被提交。
   **提交后三重验证（2026-09-14 实测有效）**：① 用 `git diff --cached --name-only` 确认本轮文件已不在暂存列表；② 其余 staged 条目数与提交前一致（该次实测提交前后其他 staged 恒为 125 条）；③ `git status --porcelain -- <本轮文件>` 无输出。三项齐过才算隔离提交成功，第 ② 项是"没顺手带走别人暂存内容"的关键证据。
   注意：未跟踪新文件**必须先 `git add`**，仅用 `git commit -- <path>` 对未跟踪文件无效（Git 只识别已跟踪文件的变更）。
7. **同一文件混有本人与他人在制改动 → 部分提交法** ★2026-09-16 实测新增（第 6 条的重要补丁）：
   - **坑在哪**：`git commit --only <pathspec>`（等价 `git commit <pathspec>`）提交的是该路径的**工作区内容**。当这个文件同时含并发会话尚未提交的改动时，第 6 条那个写法会把别人的在制工作一起带进提交。本轮实测 `grow_moc.py` 工作区 diff 106 行，其中只有 24 行是本人的（其余是并发会话的 `ac.write_committed` 重构）。
   - **判据**：先 `git diff -- <file>` 把全文导出去逐 hunk 看，凡出现自己不认识的函数/模块引用（如 `ac.*`）、命名风格突变的块，即属他人在制。
   - **正解**：构造「HEAD + 仅本人改动」的精确内容写进 index，再**不带 pathspec** 提交 index：
     1. `git show HEAD:<file>` 取基线内容
     2. 用 Python 做精确字符串替换，**每处断言命中次数**（防锚点漂移静默改错），再 `python -m py_compile` 校验语法
     3. `git hash-object -w --stdin --path <file>`，经 stdin 传 UTF-8 字节（LF 形式），绕开 `core.autocrlf=true` 的换行滤镜；记下返回的 blob sha
     4. `git cat-file blob <sha>` **回读比对**，与构造内容不一致则改用 `--no-filters` 重试（换行滤镜是本步唯一不确定项，必须闭环验证）
     5. `git update-index --cacheinfo 100644,<sha>,<file>`
     6. `git add <其余纯净文件>` → `git commit -m MSG`（**绝不带 pathspec**，一旦带上就又回到工作区内容）
   - **验证三探针**：① `git show HEAD:<file>` 中「本人标记在、他人标记不在」（如 `_clip_summary` 在、`ac.write_committed` 不在）；② 工作区文件字节未动、他人改动仍完整；③ 提交后 `git status` 仍列出他人改动（本轮 29 项 → 26 项，减的正是本人 3 个纯净文件 + grow_moc 转入 M）。
   - **状态解读**：部分提交后该文件呈 `MM`（index 为本人版本、工作区含他人改动），这是**正确状态**而非异常，不要试图"修干净"。
   - **脚本仓真实位置**：`<YOUR_SCRIPTS_DIR>\.git` 是独立 git 仓（`<YOUR_WORKBENCH>` 本身不是仓），其 master 无远端。
   - **环境前提**：Bash shim 退化时（`cd`/`ls`/`head`/`tail`/`wc`/`dirname` 全 `command not found`），git 操作一律走 `subprocess.run(args, cwd=REPO)`；**不要在 Bash 里拼 `cd` 链**——`cd "X" && git ...` 会因 cwd 未切换成功而假报 `fatal: not a git repository`，极易误判"仓库不存在"。
8. **状态归属判定与草稿/正本同步** ★2026-09-16 实测新增：
   - **坑（本轮实际踩到）**：用 `git status -s` 判"哪些是已暂存"时，若对输出行做 `.strip()` 再按字符位判断，会把 ` M <path>`（仅工作区修改、未暂存）误判成已暂存。原因很简单，` M` 的标志就在行首那个空格上，strip 一吃就消失。本轮目标文件明明未暂存，却被计入"他人暂存 2 条"，若照此误判就可能做出错误的范围判断。
   - **正解**：一律用 `git status --porcelain`（等价 `-s`）并**保留原始字符**判定，绝不做行级 strip：
     ```python
     staged    = [l for l in lines if l[0] not in " ?"]      # 首列非空格非问号 = 已暂存
     unstaged  = [l for l in lines if l[0] == " " and l[1] != " "]   # 仅工作区修改
     untracked = [l for l in lines if l.startswith("??")]
     ```
     打印时用 `repr(l)` 保留行首空格，避免人工审阅时再次被吞。
   - **纯增量修订走第 6 条即可**：当目标文件本身干净、只是追加章节时，不需要第 7 条的部分提交法。本轮单文件追加实测 `git commit -o <file>` 得 `+79/-11`，前后他人 staged 恒为 31 条、未跟踪恒为 1 条、删除条目 0。
   - **草稿与正本同步（新）**：知识库正本带 YAML frontmatter，工作区草稿不带。以正本为准修订后，必须把正本**去掉 frontmatter** 写回草稿，否则草稿静默落后、下次误读。切分用 `re.match(r"^---\n.*?\n---\n", s, re.S)`，写回后立即断言 `草稿内容 == 正本正文`，并打印两侧字节数（本轮正本 49287 B / 草稿 48532 B，差的 389 B 正是 frontmatter）。

## Phase 0.5：Obsidian 基础操作速查（查/读/写/改 vault，原 obsidian skill 并入）

> v2.0 起本 skill 是 vault **总入口**：任何「查/读/写/改/入库/展示」都从这里出发，不再单独调 obsidian skill。

- vault = 普通文件夹，**默认路径 `<YOUR_VAULT_PATH>`**；Obsidian 客户端只是它的可视化编辑器，直接读写 `.md` 文件即可，Obsidian 会自动刷新。
- 目录约定（来自用户设置）：
  - `06-<YOUR_DOMAIN>/`：分 `我的作品`（**自家项目档案**，别混）与 `灵感与素材库`（别人的作品）
  - `07-<YOUR_DOMAIN2>/`：投资学习笔记 / 标的观察
  - `AI-00~/AI-03~`：本地 AI 栈笔记（Ollama / ComfyUI / Obsidian 接入）
- 操作方式（用 WorkBuddy 自带工具，无需命令行）：
  - 查找笔记（按名/内容）：**Grep**（glob `**/*.md`）；读取：**Read**；新建/覆盖：**Write**（会覆盖，写新文件前确认路径不存在）；局部修改：**Edit**；列出目录：**Glob**（如 `06-<YOUR_DOMAIN>\**\*.md`）

## Phase 1：入库前闸门（四问 + 三不进）

### 四问闸门（入库前必过）
1. 这是结论/笔记，还是过程数据（缓存/脚本/CSV 本体）？
2. 项目目录（如 <PRIVATE_SYSTEM>\）里是不是已有原件？有就不收，只在 KB 留一句路径索引。
3. 进 KB 的只能是 .md 笔记（带 frontmatter：title/created/status/type/author/source）+ 富格式 .html 报告。缓存/脚本/CSV 一律不进。
4. MOC（地图页）链的是笔记，不是原始文件；原始文件写一句"位于项目目录 XXX"。

### 死规矩三条（不可逆底线）
- 缓存不进 KB（partial JSON、equity/trades CSV、cache_* 目录）
- 脚本不进 KB（.py 留在项目 scripts/）
- CSV 大表不进 KB（只在 KB 写摘要 + 路径）

### 防复制品操作（关键动作）
入库前对"疑似重复"文件跑 MD5 比对：
  KB 文件 vs 项目目录同名文件，`md5sum` 一致 = 复制品，直接不收。
Git Bash 命令（须 dangerouslyDisableSandbox:true）：
  md5sum "<YOUR_VAULT_PATH>/.../file.json" "<PRIVATE_SYSTEM>/scripts/file.json"
若一致，KB 只留"路径索引"，删掉复制品再提交。

### 非复制品怎么办（归档保底，别直接删）
MD5 **不一致**（项目有但版本不同）→ 不是复制品，是先前的快照。**不要直接 `git rm`**，先归档：
```bash
mkdir -p "<PRIVATE_SYSTEM>/.kb_archive/YYYY-MM-DD"
cp "KB文件路径" "<PRIVATE_SYSTEM>/.kb_archive/YYYY-MM-DD/相对路径"
# 归档完成后，再按 Phase 0.4 小批删除 KB 里的
```
项目目录**已不存在**的文件（如旧 tests/ 脚本）→ 同样是 KB 独有，先归档再删，绝不裸删。

## Phase 1.6：方法论闭环（写进 vault ≠ 永久在 ★2026-08-15 血泪教训）

> 背景：2026-08-15 实测发现 vault 主笔记 `.md` **整体丢失**——目录内所有文件 mtime 均为 00:48，疑似 Obsidian 同步/回滚把当天新写入的笔记冲掉，MOC 留下悬空引用。此前 Write/Edit 工具**都返回了成功**——但文件后来没了。
> **结论：工具成功 ≠ 文件持久。任何"已入库"声明，必须以磁盘二次验证为准。**

### 1.6.1 入库后二次验证（每次写/改 vault 后必做，不可省略）
1. `ls -la` 确认文件存在、大小合理（正文笔记通常 >1KB，几十字节多是空壳）；
2. `grep -c` 关键新内容（章节标题、核心结论句）确认真的进去了；
3. 同步验证 MOC 链接目标存在（防悬空引用）。
不要只看工具返回的"成功"，要亲眼核验磁盘状态。

### 1.6.2 vault 外正本策略（关键交付物必须双份）
- **正本** = `<WB_HOME>\preview\` 下经 md2html.py 生成的完整 HTML；
- **副本** = vault 内的 `.md`。
- 规则：重要的策略/方案/研报类交付件，**先转 HTML 落 preview 作正本，再写 vault md**；md 丢了可以从正本逆向还原（1.6.3），不会全损。
- ⚠️ **边界澄清（2026-08-28）**：本条是**归档防灾**用途，只针对重要策略/方案/研报类交付件，**不是展示环节的自动生成依据**。日常展示已按 1.6.4 改为按需生成，勿据此把每个 md 都转一遍 HTML。
- 反向提醒：preview 里有 HTML **不代表已入库**；入库状态以「vault md 存在 + MOC 接链」为准，两者缺一都要补。

### 1.6.3 逆向还原工具（md 丢失时的急救通道）
- `html2md.py`（稳定位置 `<USER_HOME>\.workbuddy\html2md.py`）：`python html2md.py <输入.html> <输出.md>`，把 preview HTML 还原成 md（保留章节、表格、frontmatter）。
- 还原后必做三件事：
  1. 修 HTML→MD 还原产生的**废链接**（`[[x]]x]` 这种拼接瑕疵，grep `\]\]` 附近人工核对）；
  2. `grep` 校验章节齐全（`grep -c "^#\{1,3\} "` 对照原结构）；
  3. 再经 md2html.py 重转 HTML，保证 md↔html 一致（防止"改 md 忘转 html"分叉）。
- 已知坑：脚本用 `skip_depth` 只跳过 `head/style/script/meta/title` 与提示框 div；`html/body/article` 等容器标签**不**触发跳过——早期版本因误跳 article 导致整篇被丢，已修复，勿回退成"见 body 就跳"的写法。

### 1.6.4 HTML 展示链路（**2026-08-28 起改为按需生成**，原 md-html-preview skill 并入）
> 用户约定（2026-08-04 建立、**2026-08-28 修订**）：**取消自动生成 HTML，改为按需生成**。默认直接 present `.md`，只有用户明确说"转 HTML / 生成预览 / 要 HTML"时才执行转换；旧规"所有 md 默认先转 HTML、禁止直接 present .md"即日解除。
> WorkBuddy 内置 md 预览器对中文路径/新写入文件报"暂无数据"，文件本身没坏；日常查看首选 Obsidian 双击 `.md`（渲染完美、零成本）。
> ⚠️ 仍有效的事实：内置浏览器面板对本地 HTML **同样空白**，所以每次真的生成了 HTML，必须明确告知用户「双击 HTML 文件」或起本地服务 `python -m http.server 8765 --directory "<WB_HOME>/preview"` 访问 `http://127.0.0.1:8765/`。

1. **工具**：转换器 `<USER_HOME>\.workbuddy\md2html.py`（纯标准库、不联网；副本 `<WB_HOME>\md2html.py`）；Python `<USER_HOME>\.workbuddy\binaries\python\versions\3.13.12\python.exe`；输出目录 `<WB_HOME>\preview\`（不存在先 `mkdir -p`）。

3. **修 obsidian:// 失效链接（如存在才处理）**：md2html.py 把 `[[wiki]]` 转成 `obsidian://open?path=...` 协议链接，离开 Obsidian 在 HTTP 浏览器点击会失效。⚠️ 2026-08-15 实测：**`fix_obsidian_links.py` 在机器上两处 `.workbuddy` 目录均不存在**（skill 文档此前有误）；且 md2html.py 产出的报告 HTML 常含 **0 个** obsidian:// 链接（wikilink 已就地处理）——先 `grep -c 'obsidian://' <html>` 确认，有才处理。缺失脚本时用内联 Python 替换：

## 节奏：分仗打，不混着清
- 一仗一主题；先调查（MD5 / 清单 / 链接扫描）再动手，每仗单独 git 提交。
